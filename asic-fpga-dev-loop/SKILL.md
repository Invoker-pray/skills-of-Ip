# ASIC/FPGA 设计迭代全循环

一次迭代 = 一个可交付增量，走完以下全部阶段；每个阶段有明确的
产出、责任分工和失败分流。**一次迭代只改一个变量**（一个 RTL 改动、
一个默认值翻转、一个 driver 行为），多变量叠加会毁掉 A/B 归因。

```
设计/修改 RTL → 三层仿真 → 全回归+bit-exact 仿真 → Vivado 构建
    ↑                                                    ↓
优化方向判断 ← 结果分析 ← 自动上板（打包/上传/初始化/SSH 测试）
```

## 阶段 0：接手上下文

使用 `/projsync` 完成远程同步、作用域 claim 和 `docs/handle.md` 交接；如果项目存在 `docs/project-overrides.md`，先按其中明确的开发闭环和验证规则执行，本 skill 只补充未被覆盖的硬件环境上下文。读取 memory 中的 license、路径和板卡信息，确认本次迭代的**单一变量**及预期收益，并在 projsync checkpoint 中记录。

## 阶段 1：设计 / 修改 RTL（或 driver）

修改前先写清本次改动预期改变的时序、数据流或资源使用，明确预期收益和可能副作用。若涉及接口或数值语义变化，先同步更新 Python golden model、driver mock 和 testbench 期望值，再修改 RTL；修改后检查原有协议、时序关系和边界条件仍然成立。

- 改动前先证明改动的正确性（位精确论证、时序关系推演），写进设计
  说明；"跑了仿真再说"不算论证。
- 保持改动面最小。新逻辑与旧机制复用同一抽象时，检查旧机制的所有
  隐式依赖（状态寄存器是否被多个流水段共享？清零时机是否随改动
  改变？——一物两用的指针在流水重叠下会反噬，见 pitfalls）。
- 竞态排查清单：任何新引入的"提前/推后"时序，逐个检查它影响到的
  每个信号采样点：采样的是改动前还是改动后的值？注册脉冲 vs 组合
  脉冲差一拍，bank/tag/ready 类清理逻辑就会打错目标。
- 跨流水段的"许可/凭证"信号必须显式建模为锁存许可证（发射点置位、
  消费点清零），不要复用含杂散脉冲或粘滞位的状态信号做或运算兜底。
- 同时更新对应的 testbench 期望值，并检查 TB 是否引用了被改动/删除
  的内部信号（编译错会在最意想不到的门禁出现）。
- **契约级改动**（对外行为/数值语义变化，而非纯实现优化）：先更新
  golden model 和 driver mock，RTL 向 golden 对齐——golden 是位精确
  的锚，锚先动。

## 阶段 2：三层一致仿真（AI 写代码并自查，用户跑长门禁）

**分工规则**：长运行任务（python golden 全量、verilator lint 全量、
VCS 回归、Vivado build）一律给用户可复制的命令块 + 判定标准，等结果。
AI 自己跑的只有短命检查：单元测试、语法 lint、单模块冒烟、grep、
用脚本复算 RTL 组合逻辑的期望值。

**期望值复核是廉价高收益步骤**：新组合逻辑用几十行 Python 模拟，
逐 case 核对 TB 期望值（含边界情形——"正向断言"实为"负向 guard"
的 case、partial tile 与 cap 的优先级交互都实测过抓出错期望）。

三层各自回答一个不同的问题，缺一不可：

| 层 | 命令（LARA 实例见 references/lara-commands.md） | 回答的问题 |
|---|---|---|
| Python golden | `golden --test-all` | 数学/数值语义对不对 |
| Verilator lint | `--lint-only -Wall` 全文件 | 语法/位宽/新引入的坏味道 |
| VCS 回归 | `run_regression.sh` 全量 | FSM/协议/集成行为对不对 |

- **Verilator 判据用"与 HEAD 基线归一化后 warning 集合 diff 为空"**，
  不是绝对零（老代码总有 pre-existing 噪声）；归一化 = 去掉行号后
  排序比对。新增任何一条 warning 都要弄清来源。
- lint 挂了不一定是 RTL：TB 引用被删信号、$display 格式串与参数
  不匹配，都会在最意想不到的地方报错。
- 用 Python/脚本复算新逻辑的期望值（组合逻辑用几行 Python 模拟），
  核对 TB 期望值——TB 期望值本身可能写错（包括"正向断言"变"负向
  guard"的边界情形）。

## 阶段 3：全回归 + bit-exact board-case 仿真

- 全回归判定标准是精确字串（如 `Passed: 28 / 28` + `ALL TESTS PASSED`），
  不能只看退出码。
- **bit-exact board-case 矩阵绝不抽样**。长度 × 模式 × position base
  的组合各触发不同的流水路径；只跑 L512 抽样放过过 L32/L128 的真实
  bug。改了什么就跑全矩阵，两组 case root × 全长度。
- 回归里新增/修改的 TB 检查，必须在同一提交里实际跑过一次（带 plusarg
  的门控检查如果 CI 只跑默认模式，等于不存在）。
- **长仿真输出重定向到文件**（`> /tmp/run.log 2>&1`），不要管道接
  `head`——管道关闭触发 SIGPIPE 杀掉仿真，日志冻结在半途像挂死。
  看头部用 `grep ... 文件 | head`。

## 阶段 4：Vivado 构建

- 构建前把 RTL 提交到 develop（干净 HEAD），让 `build_metadata.txt`
  记录 commit 哈希和状态——bitstream 与源码的可追溯性靠它。
- 构建 tag 目录用日期命名，**永不覆盖旧 build 目录**（失败构建也是
  证据）。
- 判定：WNS ≥ 0、TNS/WHS/THS 全零、DRC 0 Errors（DRC 0 不等于无
  warning，DSP 流水 advisory 是常态）。
- 时序余量薄（<0.1ns）时，任何新增组合路径都要在提交信息里预告，
  构建WNS 变化与预告对照。
- bit/hwh/xsa 的 SHA256 记入版本记录；**作废的 bitstream 明确宣布
  作废**，防止误用（改一版 RTL 后旧 bit 立即失效）。
- 外部板测或评测可能晚于源码提交；使用 `/projsync` 的两阶段证据记录，先标记 pending，再把实测结果写回交接记录。

## 阶段 5：自动上板

完整流程与所有已知坑的实操细节见 `references/lara-commands.md`。骨架：

1. **打包**：打包脚本 + 手动补 case/数据目录（打包脚本经常只打印
   cp 提示不代拷）+ 重生成 SHA256SUMS + 本地校验。
2. **上传**：scp 整目录（注意目标已存在会嵌套一层）；SSH/SCP 密码
   只经 pexpect 环境变量传递，**永不写入文件/脚本/Git**。
3. **初始化**：板子每次重启后 fabric overlay 不会自动加载——
   **初始化/清缓存脚本（含 dtbo 插入）必须是测试脚本第一步**，
   否则全部 case 假 FAIL（ENODEV）。
4. **执行**：sudo 需显式注入环境变量（XRT 路径等），无 tty 需
   `ssh -tt` + pexpect 应答（expect 模式记得转义 `[sudo]`）；
   性能测量显式固定请求模式等环境口径；长任务 nohup/前台 + 轮询。
5. **取回**：结果目录 + profile + 运行脚本 + 环境快照一起取回本地
   归档（独立目录，不覆盖历史）。

## 阶段 6：结果分析（三分流）

拿到板上/仿真结果后，按顺序三分流，**不要跳步直接看性能数字**：

### 6a. 运行/环境问题 → 修板上侧
症状：ENODEV、设备找不到、权限错、overlay 加载失败、全部 case 同一
异常。处理：修板上初始化脚本/udev/dtbo/镜像构建脚本，必要时升级
打包流程；**这类问题不许改 RTL**。修完把坑写进 pitfalls 并固化进
初始化脚本。

### 6b. 逻辑/RTL 错误 → 回宿主机仿真复现
症状：bit mismatch、输出错位、挂死、计数对不上。**完整方法学与
真实战例见 `references/debug-playbook.md`（读它再动手）**。骨架：
1. **确认板上环境正常后，若判断为 RTL/逻辑问题，优先在宿主机仿真环境完整稳定复现**（VCS board-case 单 case），禁止在板上试错改 RTL。板上失败但仿真通过时，先检查覆盖缺口（哪个长度/模式没跑过）、真实 DMA 延迟、存储器时序、重启环境以及板上环境是否正常，再判断是否存在仿真覆盖或硬件差异。
2. **消融实验圈定范围**：把可疑新机制整体置 0，全对则问题确定在
   该路径内（排除数据/环境），缩小搜索空间。
3. **事件级 dump + 模式对比**：在具体生命周期节点（launch/完成/退役/
   边界/mac_start）加边沿触发 $display 带完整上下文，对比健康与
   异常单元；**多源条件必须打印每个源在该拍的值**（三源或的触发
   无法归因时不打印每个输入就是瞎猜）。使用输出守恒计数（beats got vs
   expected）定位具体节点，先把"随机损坏"与"系统性少做工作"分开。
4. 修复后：单 case 确认 → 全回归 → **全矩阵**（不抽样）→ 重新
   Vivado → 重新上板。debug 打印用完即删，不留进提交。
5. 根因与教训写进 pitfalls（现象、根因、修复、可泛化的规则）。

### 6c. 结果有效 → 逻辑自洽性审查 → 瓶颈判断
1. **口径审查**：各指标是否同口径可比（PL transaction ≠ core active
   ≠ host E2E ≠ CPU baseline）；统计是否 median/geo 口径一致；是否有
   统计错误（几何平均忘开 N 次方根、百分比忘 ×100、对照样本被污染——
   执行用户不同导致隐式模式切换是真实案例）。
2. **因果审查**：收益/回退能否用改动机理定量解释？MAC cycles 按预测
   降但 E2E 不动 = 收益被别的瓶颈吸收——这本身就是重要发现。
3. **瓶颈判断**：用 cycle 分解（compute/stall/DMA 固定开销/请求延迟）
   定位主导项；"计算占比上升后某优化兑现率提高"这类迁移结论要写进
   路线。判断必须绑定可复现的输入、运行口径、源码 commit、bitstream
   哈希和结果证据；没有这些证据时只能记录为待验证假设。
4. **优化方向**：优先从已确定的路线选（单变量、可量化预测）；需要
   外部输入时搜索同类设计（注意记录检索关键词与适用边界，不把论文
   收益当本项目预期）。
5. **分层策略**：不同长度/规模区间的主导瓶颈不同（短序列 host-bound、
   长序列 compute/stall-bound 是常见形态）——优化按区间分治，收益
   预测也按区间给，一项优化极少全区间生效。
6. 结论写回版本记录/路线文件 → 本地 commit + tag；远程 push 只有在用户明确要求时执行 → 回阶段 1。

## 失败分流速查

| 症状 | 分流 | 首选动作 |
|---|---|---|
| 全部 case 同一环境异常 | 6a | 修初始化脚本/环境，查 dmesg |
| bit mismatch，仿真可复现 | 6b | 事件 dump 定位 → 修 RTL |
| bit mismatch，仿真不可复现 | 6b+ | 查仿真/硬件差异（XPM 时序、真实 DMA 延迟），加长仿真覆盖 |
| 收益为零但工作量按预测下降 | 6c | 查该瓶颈是否已被其他项吸收（stall 守恒分析） |
| 数字自相矛盾 | 6c | 先查统计口径和对照污染，再查 RTL |

## 红线（违反过、代价真实）

- 不把抽样验证当全量验证；不放行未跑过 board-case 矩阵的 RTL。
- 不在板上调试 RTL 逻辑问题。
- 不把作废 bitstream 当当前基线。
- 不把 mock/VCS/板测结果混写成一个口径。
- 长门禁命令必须附环境导出和判定标准；VCS 空日志 + exit 255 =
  license 没开，先查服务再下结论。
- 板卡、license 和部署环境使用前必须声明占用；并行实验使用独立 worktree。
- 密码、API key、SSH 凭据永不写入文件、日志或 Git。
- `/tmp` 中需要长期保留的日志必须复制到可追溯目录；不得 reset 或覆盖其他成员的未提交修改。
